## Implementation

### CAU

`VenusLane` now owns a `CauResultQueueDepth = 2` FIFO.  Each entry carries:

- vd1 and vd2 data;
- mask;
- instruction and running-ID tag;
- independent vd1/vd2 writeback completion state.

The arithmetic pipeline publishes only when the FIFO has space.  A full FIFO
holds the paired pipeline head and tag.  The queue head independently
arbitrates the two VRF writeback passages.  The prior CAU RAW result hold and
pipeline-shape ownership rules remain in force.

### SerDiv

`VenusLane` now owns a `SerDivResultQueueDepth = 2` FIFO.  Each entry carries
result data, mask, instruction/running-ID tag, enqueue tick, and writeback
state.

SerDiv uses a separate queue-service event.  It does not reuse or shorten the
data-dependent iterative completion event.  An entry cannot dequeue at its
enqueue tick, which preserves the RTL registered boundary even if two gem5
events share an edge.  A full FIFO holds the completed iterative result until
space becomes available.

## Grant-backpressure capacity test

Response latency cannot exercise this contract: a response may be delayed
after the request was already granted.  R51 therefore exposes the existing
one-nanosecond `SimpleMemory` request acceptance interval as a generic
`request_gap` parameter.  Its default remains `1ns`.

For testing only, `VENUS_GEM5_VRF_GRANT_GAP` applies `request_gap` to physical
VRF data and mask banks.  It does not affect tile SPM, shared L2, DMA,
instruction behavior, addresses, PCs, or payload values.  Normal runs that
do not set the variable retain the historical one-nanosecond behavior.

The isolated program is generated by:

`tools/venus_vfu_result_queue_microbench.py`

It executes two broadcasts, one add, and one divide, with barriers separating
VFU classes.  The automated sweep and verdict are produced by:

`tools/run_venus_vfu_result_queue_capacity.py`
